## 1. Statistical body models: what they are, size, and exact licence terms

### Takeaway
Every Max-Planck model (SMPL, SMPL-X, STAR, SUPR, SKEL) is non-commercial AND explicitly non-redistributable, so none of them can be committed to a public GitHub repo or served from GitHub Pages; GHUM is request-form only with no published licence text. The only statistical/parametric bodies that are openly redistributable are Anny (Apache-2.0 code + CC0 MakeHuman assets, first released 5 Nov 2025) and Meta's MHR (Apache-2.0, released Nov 2025), plus NVIDIA's SOMA-X wrapper (Apache-2.0).

### Inferences
- Publishing SMPL, SMPL-X, STAR, SUPR or SKEL model files (template + shape blendshapes) in a public repo or on a public website would breach the "No Distribution" clause even for a non-commercial hobby project; the non-commercial grant covers use, not redistribution. The CC-BY "SMPL-Body" carve-out explicitly excludes shape blendshapes, so it yields at most fixed-shape meshes, which is useless for a measurement-driven mannequin.
- For a browser app the realistic candidates are therefore: (a) MakeHuman/MPFB2 CC0 assets used directly, (b) Anny as an offline (Python) authoring tool on top of the same CC0 assets, (c) MHR (Apache-2.0). MHR's 45 identity parameters are PCA-like and not tied to tailor measurements, and its asset format (FBX + npz + TorchScript, neural correctives) is heavier to port than MakeHuman's plain per-vertex offset targets.
- Anny's parameters are anthropometric in the "phenotype" sense (age, height, weight, muscle, proportions), not tailor measurements; its own measurement code covers only height, waist, volume/mass/BMI. Driving 25 girths needs additional machinery (section 3/6).

### Gaps
- The exact current wording of the SMPL model licence, the SMPL-Body CC-BY 4.0 licence and STAR/SUPR/SKEL website licence pages could not be opened (hosts blocked); GitHub copies of the SMPL-X, STAR, SUPR and SKEL licences were used instead. No GitHub-hosted copy of the original SMPL model licence was found.
- GHUM licence terms: no licence text is published in the repository and the request form could not be opened. Treat as "not openly redistributable" until proven otherwise.
- MHR: the size of the release assets, and the text of the licence file added to the assets in v1.0.1, were not readable (release asset list returned HTTP 403 to the automated client). The repo-level licence is Apache-2.0; confirm the asset-level LICENSE before shipping MHR data.

## 2. Open assets: MakeHuman/MPFB2, Blender Studio base meshes, MB-Lab, Mixamo/Ready Player Me, CAESAR-derived models, scans

### Takeaway
MakeHuman/MPFB2 is the only asset set found that is simultaneously (i) CC0, (ii) realistic human anatomy, and (iii) already shipped with tailor-style "measure" morph targets (20 measurements × incr/decr) plus gender/age/weight/muscle/height/proportion macro targets; only the application code is (A)GPL, and the project states explicitly that assets and exports are unrestricted. Blender Studio's Human Base Meshes are CC0 but are static sculpting bases with no morphs; MB-Lab's data is AGPL-3 and propagates to generated models; Mixamo forbids redistributing raw character files; Ready Player Me shut down on 31 Jan 2026; CAESAR-derived models are non-commercial.

**MakeHuman "measure" targets and macro targets**
- The measurement modifier group defines exactly 20 measures, each with a `decr` and `incr` target: neck-circ, neck-height, upperarm-circ, upperarm-length, lowerarm-length, wrist-circ, frontchest-dist, bust-circ, underbust-circ, waist-circ, napetowaist-dist, waisttohip-dist, shoulder-dist, hips-circ, upperleg-height, thigh-circ, lowerleg-height, calf-circ, knee-circ, ankle-circ **[read directly]** — [measurement_modifiers.json](https://github.com/makehumancommunity/makehuman/blob/master/makehuman/data/modifiers/measurement_modifiers.json)
- MakeHuman measures each quantity with a hard-coded "Ruler": a fixed list of base-mesh vertex indices per measurement (e.g. a 20-vertex loop for thigh, calf, knee, ankle, upper arm and wrist; two vertices for lengths such as nape-to-waist `[1491,4181]` or shoulder distance `[7478,8274]`); the value is the summed Euclidean edge length along that vertex list, ×10 for centimetres **[read directly]** — [0_modeling_a_measurement.py](https://github.com/makehumancommunity/makehuman/blob/master/makehuman/plugins/0_modeling_a_measurement.py)
- When the user types a value, MakeHuman runs a bisection on that one slider in [-1, 1]: up to 10 halving steps, stopping when `fabs(measure - goal) < 0.01` (cm), re-applying the modifier and re-measuring each step **[read directly: `MeasurementValueConverter.displayToData`]** — [0_modeling_a_measurement.py](https://github.com/makehumancommunity/makehuman/blob/master/makehuman/plugins/0_modeling_a_measurement.py)
- Size of the measure targets **[measured in the Anny-bundled MPFB2 data]**: 40 files, 475 KB gzipped in total. Circumference targets are sparse and local: e.g. waist-circ moves 1,518 vertices (862 on the body), thigh-circ 890–1,096 (≈550 body), calf-circ 776 (404 body), wrist-circ ≈550 (≈470 body), bust-circ ≈1,900 (≈1,200 body). Length targets are large because everything beyond the segment translates: napetowaist-dist ≈13,200 vertices (≈10,000 body), upperleg-height ≈5,400, neck-height ≈5,500 — [anny 0.6.2 on PyPI](https://pypi.org/project/anny/)
- Macro targets **[measured]**: 348 files, 32.8 MB gzipped; they are dense (≈14,900 vertices moved on average). The set is 72 "universal" gender×age×muscle×weight targets (`universal-{female,male}-{baby,child,young,old}-{min,average,max}muscle-{min,average,max}weight`), 144 height targets (…-`{min,max}height`), 108 proportion targets (…-`{ideal,uncommon}proportions`) and 24 race×gender×age targets. Restricting to the `young` age anchor: 18 universal targets = 0.83 MB gz, 36 height targets = 5.0 MB gz, 36 proportion targets = 2.4 MB gz — [anny 0.6.2 on PyPI](https://pypi.org/project/anny/)
- Other local CC0 targets relevant to tailoring exist besides `measure-*` **[measured]**: per-limb `{l,r}-{upperarm,lowerarm,upperleg,lowerleg}-{fat,muscle}-{decr,incr}` and `-scale-{depth,horiz,vert}`; `torso-scale-{depth,horiz,vert}`, `torso-vshape`, `torso-muscle-{dorsi,pectoral}`; `hip-scale-{depth,horiz,vert}`, `hip-waist-{up,down}`; `stomach-tone`, `stomach-pregnant`; `buttocks-volume`; 228 breast targets; `head-scale-{depth,horiz,vert}`; `{l,r}-foot-scale` — [anny 0.6.2 on PyPI](https://pypi.org/project/anny/)

## 3. Measurements-to-shape methods (research and industry)

### Takeaway
Research maps measurements to shape with a learned linear (or low-order polynomial) regression from a handful of measurements to PCA shape coefficients, optionally followed by an optimisation that refines the mesh until measured values match; industry tools (CLO, Browzwear, Style3D, MakeHuman) instead expose per-measurement fields backed by local morphs, let unassigned measurements follow scan-derived statistics, and accept small residual errors. Girths are measured either along fixed vertex loops or, more robustly, by slicing the mesh with a plane, keeping the slice of the right body part, and taking the convex-hull perimeter to imitate a taut tape.

### Cited Findings

**Research lineage**
- Allen, Curless & Popović, "The space of human body shapes: reconstruction and parameterization from range scans", ACM TOG 22(3), 2003, pp. 587–594; companion "Exploring the space of human body shapes: data-driven synthesis under anthropometric control" (SAE DHM 2004). Per Wuhrer & Shu's review, such methods learn "a linear or near-linear mapping between the training set of human shapes and the parameter space of measurements" and use it to produce a shape for a new set of measurements **[search summary only]** — [Wuhrer & Shu, arXiv:1109.1175](https://arxiv.org/abs/1109.1175)
- Seo & Magnenat-Thalmann, "An automatic modeling of human bodies from sizing parameters", I3D 2003, pp. 19–26: template mesh + database of scanned people **[search summary only; method details not verified]** — [cited in Wuhrer & Shu, arXiv:1109.1175](https://arxiv.org/abs/1109.1175)
- Wuhrer & Shu, "Estimating 3D Human Shapes from Measurements" (Machine Vision and Applications 24, 2013): goal is "to predict shapes that are inside the space of human shapes, but still account for local variations not captured by the training data", in contrast to earlier statistical methods that "limit the generated shapes to the space spanned by the shape model" **[search summary only]** — [arXiv:1109.1175](https://arxiv.org/abs/1109.1175); [Springer](https://link.springer.com/article/10.1007/s00138-012-0472-y)
- Yang, Yu, Zhou, Du, Davis & Yang, "Semantic Parametric Reshaping of Human Body Models", 3DV Workshops 2014, pp. 41–48: scans are put in correspondence by non-rigid template deformation and a local model is learned so individual body parts can be reshaped by semantic parameters **[search summary only]** — [dblp](https://dblp.uni-trier.de/rec/conf/3dim/YangYZDDY14.html); [University of Kentucky record](https://scholars.uky.edu/en/publications/semantic-parametric-reshaping-of-human-body-models/)
- Virtual Caliper (Pujades et al., IEEE TVCG 2019): establishes which body measurements users can reliably take on themselves with VR controllers, finds several distance measurements, and verifies "that these are linearly related to 3D body shape as represented by the SMPL body model" **[search summary only]** — [Virtual Caliper project page](https://virtualcaliper.is.tue.mpg.de/)
- Sengupta et al. (BMVC 2021) "define the mapping from measurements to SMPL β to be a linear regression", so a Gaussian over measurements maps analytically to a distribution over betas **[search summary only]** — [arXiv:2111.15404](https://arxiv.org/abs/2111.15404)
- A baseline study fits a linear model that predicts 15 SMPL-derived body measurements from only self-reported height and weight, separately for males and females **[search summary only]** — [PMC8914647](https://pmc.ncbi.nlm.nih.gov/articles/PMC8914647)
- SHAPY (Choutas et al., CVPR 2022): body shape "represented as SMPL-X parameters or metric measurements, i.e. height, weight and chest/waist/hip circumference"; its Attributes-to-Shape (A2S) model "predicts SMPL-X shape parameters from attributes (a), attributes + height (b), and attributes + height + chest + waist + hips" **[read directly]** — [SHAPY README](https://github.com/muelea/shapy); the paper fits second-degree polynomial regressions trained on CAESAR, gender-specific **[search summary only]** — [arXiv:2206.07036](https://arxiv.org/abs/2206.07036). SHAPY code/models are under the MPI "non-commercial scientific research purposes" licence **[read directly]** — [SHAPY README](https://github.com/muelea/shapy)
- A2B ("Leveraging Anthropometric Measurements to Improve Human Mesh Estimation…", 2024): a learned model that converts 36 tailor-style anthropometric measurements to SMPL-X shape parameters; the authors note betas are PCA components with no direct physical meaning, so the mapping must be learned **[search summary only]** — [arXiv:2409.17671](https://arxiv.org/abs/2409.17671)
- AnthroNet (Unity, 2023) goes the other way (betas/shape → dense anthropometric measures) and conditions human generation on anthropometrics **[search summary only]** — [arXiv:2309.03812](https://arxiv.org/abs/2309.03812)
- GarmentCodeData (Korosteleva et al., 2024) samples body shapes from a PCA model and computes tailoring measurements per shape for made-to-measure sewing patterns; its "GarmentMeasurements" tool does `./generate_shapes` (PCA sampling) and `./measurements output.obj measurements.yaml` **[read directly]** — [GarmentMeasurements README](https://github.com/mbotsch/GarmentMeasurements)

**How girths are measured on a mesh**
- Standard approach: "Computing circumferences involves "slicing" the mesh with a plane by computing the intersection of the triangles of the mesh with the plane. The intersection gives a closed contour and the length of this contour gives the circumference." **[search summary only; from a body-shape patent text]** — [US patent 9,189,886 "Method and apparatus for estimating body shape"](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/9189886)
- Convex hull: taking the convex hull of the intersection "may correspond better to the measurements obtained by a standard tape measure on the real body"; SHAPY computes circumferences by intersecting the mesh with a plane through a landmark vertex, taking the convex hull of the intersection points and using its perimeter **[search summary only]** — [US patent 9,189,886](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/9189886); [SHAPY, arXiv:2206.07036](https://arxiv.org/abs/2206.07036)
- SMPL-Anthropometry (open-source, measures SMPL/SMPL-X): "Lengths are defined as distances between landmark points defined on the body model"; "Circumferences are defiend as plane cuts of the body model"; the cutting plane is "defined by a point (landmark point) and normal (vector connecting the two joints)"; "a possible issue that arises is that the plane cutting results in multiple body part slices. To alleviate that, define the body part where the measurement should be located… only the slice in the corresponding body part is used" **[read directly]** — [SMPL-Anthropometry README](https://github.com/DavidBoja/SMPL-Anthropometry)
- SMPL-Anthropometry's 16 standard measurements: head, neck, chest, waist, hip, wrist, bicep, forearm, thigh, calf and ankle circumferences; shoulder-to-crotch height, arm length, inside-leg height, shoulder breadth, height **[read directly]** — [SMPL-Anthropometry README](https://github.com/DavidBoja/SMPL-Anthropometry)
- Plane placement refinements reported in the literature: shift the plane in small steps and take a local maximum (bust, hip) or minimum (waist) of hull length; select the largest closed polyline if several are found; waist is the least consistent landmark because preferred waist height varies with body shape **[search summary only; individual papers not opened]** — [GarmentCodeData, arXiv:2405.17609](https://arxiv.org/abs/2405.17609); [arXiv:2409.17671](https://arxiv.org/abs/2409.17671)
- Fixed vertex-loop alternative: MakeHuman sums edge lengths along a fixed vertex list per measurement, and Anny does the same for the waist (46-vertex loop) **[read directly]** — [MakeHuman measurement plugin](https://github.com/makehumancommunity/makehuman/blob/master/makehuman/plugins/0_modeling_a_measurement.py); [anny/anthropometry.py](https://github.com/naver/anny/blob/main/src/anny/anthropometry.py)
- A three.js forum thread discusses exactly this problem in the browser (intersection points for circumference on a human body plus convex hull) **[search result title only]** — [three.js forum](https://discourse.threejs.org/t/points-of-intertersection-for-circumfernce-measurement-on-human-body-and-use-of-convex-hull/60868)

### Inferences
- Which measurements matter most: across SHAPY (height, weight, chest, waist, hips), CLO (height + bust/under-bust as the two anchors), SMPL-Anthropometry's 16 and MakeHuman's 20, the consistent first tier is height, chest/bust, waist, hip; second tier is segment lengths (inseam, arm length, shoulder breadth, nape-to-waist); third tier is limb girths (thigh, calf, bicep, neck, wrist, ankle). A sensible solver order is therefore: global scale/height and segment lengths first, then the big torso girths, then limb girths, then small corrective passes.
- Two-layer design that mirrors both research and CAD tools: (1) a few global "macro" parameters (gender blend, weight, muscle, proportions) fitted by least squares so that the body is plausible and unassigned measurements fall back to statistically sensible values (the CLO behaviour); (2) one local morph per user-entered measurement, solved to tolerance (the MakeHuman behaviour).
- A fixed vertex loop is fast and differentiable but is neither planar nor a taut tape; plane-slice + convex hull is closer to how a tailor measures (bridges the bust cleavage, spine channel and buttock cleft) and is topology-independent. For a mannequin whose rings are authored by us, a hybrid works: use the fixed loop to locate the level, then slice + hull to report the value.
- PCA-beta regressors (Virtual Caliper, SHAPY A2S, A2B) all need a learned scan-based model (SMPL/SMPL-X/CAESAR) that the project cannot legally ship; the *method* (linear map from measurements to shape coefficients, then refine) can still be reproduced on CC0 MakeHuman targets by numerically computing the Jacobian d(measurements)/d(target weights).

## 4. Procedural / analytic alternatives when no base mesh is used

### Takeaway
Apparel-CAD literature does build mannequins without a sculpted mesh — feature cross-sections (neck, bust, waist, hip girths) fitted with spline curves and lofted, with a spline tension or section-shape parameter controlling fullness — and these are girth-exact by construction, but the cited work derives its section shapes from body scans; purely elliptical sections are the main reason a lofted model looks artificial.

### Cited Findings
- Wang, Qin, Guan & Yu, "Parametric human body model for digital apparel design": a feature-based parametric approach from 3D body scans; "automatic extraction approach of semantic feature cross-sections is developed based on the hierarchy", then "an interpolation approach of key points which fit cardinal spline to cross-section for each body part, in which tension parameter is used to represent the simple deformation of body shape"; output importable to CAD **[search summary only]** — [Northumbria University record](https://researchportal.northumbria.ac.uk/en/publications/parametric-human-body-model-for-digital-apparel-design/); [NTU IRep PDF](https://irep.ntu.ac.uk/id/eprint/37367/1/14560_Guan.pdf)
- Wu & Zhang (2008), "A Parameterized Mannequin for Apparel Design": structure built on mid-neck girth, breast girth, waist girth and hip girth **[search summary only]** — [JFBI 1(2)](https://admin.global-sci.org/uploads/Issue/JFBI/v1n2/JFBI-1.2.5_short.pdf)
- A resizable trouser-template paper extracts sectional curves at girth locations from a scan and, because "the extracted curves are neither continuous nor sufficiently smooth", redraws them as modified B-spline curves which are then grouped for scaling **[search summary only]** — [MMU e-space PDF](https://e-space.mmu.ac.uk/596356/2/Resizable%20Trouser%20Template%20for%20Virtual%20Design%20and%20Pattern%20Flattening.pdf)
- A 2021 mannequin-fabrication paper lofts a mannequin through fifteen spline curves generated from mean section points **[search summary only]** — [IJCST, doi:10.1108/IJCST-05-2020-0076](https://www.doi.org/10.1108/IJCST-05-2020-0076)
- A NURBS-based parametric calf model with key-position labelling reports an average error of 0.37% over 260 subjects **[search summary only]** — [PolyU: Xiong et al., Fast NURBS-based parametric…](https://ira.lib.polyu.edu.hk/bitstream/10397/96980/1/Xiong_Fast_NURBS-based_Parametric.pdf)
- A further classic reference surfaced by search (not opened, content unverified): C.C.L. Wang's parametric human/mannequin design paper — [mewangcl.github.io/pubs/CADParaHuman.pdf](https://mewangcl.github.io/pubs/CADParaHuman.pdf)
- MakeHuman itself shows what "local shape controls" look like when authored by artists rather than analytic: per-segment `scale-depth`, `scale-horiz`, `scale-vert`, `fat` and `muscle` targets for each limb, torso, hip, head and foot **[measured file list]** — [anny 0.6.2 on PyPI](https://pypi.org/project/anny/)

### Inferences
- Techniques that make a lofted model read as human (engineering judgement; no single source retrieved states these as a list, so treat as recommendations rather than cited fact): (1) replace ellipses by asymmetric closed splines with separate front/back depth and side-width radii and a flatness/"squareness" exponent per level (superellipse-like), e.g. flat back + rounded front at the chest, flat front + rounded back at the seat; (2) add scan-informed non-convex features — spine groove, bust separation, gluteal cleft — which also makes the difference between raw perimeter and tape (convex hull) measurement realistic; (3) use many more key levels than tailor measurements (shoulder slope, armpit, under-bust, high hip, crotch, gluteal fold, mid-thigh, knee, calf max, ankle min) and interpolate section *shape parameters* with monotone splines along the height; (4) blend limb–torso junctions (armpit, crotch, neck–shoulder) with a single skinned mesh or implicit/metaball blending + remeshing instead of intersecting tubes; (5) run one or two Catmull-Clark/Loop subdivision steps on a coarse control cage so silhouettes are smooth; (6) keep girth exactness by rescaling each section to the target perimeter after shaping (perimeter is 1-D monotone in a uniform radial scale, so a few Newton/bisection steps suffice).
- A procedural model can hit every girth exactly at its own section, but head, hands, feet, shoulders/clavicles, knees and the torso–limb junctions are what viewers judge realism by, and these are the parts that are expensive to do analytically. A hybrid is possible: sculpted CC0 head/hands/feet (cut from the MakeHuman mesh) attached to a lofted torso/limbs — but seams and shading continuity then become the main effort.
- Section shapes for a better procedural model can be harvested legally from the CC0 MakeHuman mesh: slice it at each level for several macro settings (min/avg/max weight × gender) and store normalised section curves; the procedural model then interpolates real human cross-sections instead of ellipses.

### Gaps
- No primary text was opened for any of the apparel-CAD papers; method details beyond the abstracts are unverified.
- No citable source was retrieved for metaball/implicit blending of limb junctions or for superellipse section models specifically in dress-form design; these remain engineering suggestions.
- No published anthropometric table of cross-section *shape* (depth/width ratio per level by size) was retrieved in this pass; a sibling research note on body proportions may cover it.

## 5. How virtual try-on and garment CAD tools present avatars

### Takeaway
Professional garment CAD (CLO, Browzwear, Optitex, Style3D, Alvanon) presents a parametric or library avatar with typed measurements and visible measurement lines — a fit form first, a character second — and evidence on consumer try-on suggests that more realism is not automatically better: higher photorealism raised trust in one small study, while a 2025 meta-analysis found realism alone does not guarantee a positive experience.

### Cited Findings
- CLO's avatar is edited by typed circumferences/heights/lengths with scan-driven fill-in of unassigned measures and a dedicated "Fitting Suit" section in the Avatar Editor **[search summary only]** — [CLO: Adjust Avatar Size](https://support.clo3d.com/hc/en-us/articles/33854094900633-Adjust-Avatar-Size)

- Browzwear offers both parametric avatars (measurement tab + morph sliders) and, since a 2020 update, more realistic avatars for presentation **[search summary only]** — [Browzwear avatars overview](https://browzwear.com/explore-browzwear-avatars); [Fashion Mannuscript, 26 Oct 2020](https://www.mannpublications.com/fashionmannuscript/2020/10/26/browzwear-update-includes-realistic-avatar/)

### Inferences
- For a size-and-fit tool the expected look is a matte, neutral-coloured, faceless-or-neutral-faced body with correct anatomy and proportions, optionally with tape lines drawn at the measured levels (as on AlvaForms and CLO's measure display). This is exactly what an untextured MakeHuman-derived mesh with a single clay/satin material gives, and it avoids skin textures, hair, eyes, nudity detail and uncanny-valley risk. Realism should come from silhouette and surface form (shoulders, bust, seat, knees, calves), not from textures.
- Showing the measurement loops on the body doubles as verification UI: the user can see where "waist" or "high hip" is being measured, which addresses the known inconsistency of waist placement.
- Because the base mesh is anatomically complete, a fashion app should use a neutral underwear/"fitting suit" surface (the helper-tights geometry or a smoothed variant) or a mannequin-style material to keep the display modest; Anny's default topology already applies "minor nudity-related mesh edits".

- Vendor product pages were not opened; screenshots/visual conventions (colours, default materials) are described from general documentation summaries, not verified imagery.
- Consumer-facing size tools (e.g. retailer fit finders) were not surveyed individually in this pass.

## 6. Practical guidance: effort, risk, data size, and enforcing exact circumferences

### Takeaway
The lowest-risk route to "looks human and matches typed girths" is: ship the CC0 MakeHuman body (≈13.4k vertices) with a curated subset of CC0 targets (macro + 20 measure morphs + a few limb/head/foot scale targets), blend on the CPU, measure with plane-slice + convex hull, solve morph weights with damped Gauss–Newton (or MakeHuman-style per-slider bisection), and finish with a small bone-local radial scaling pass to drive the residual to zero. Statistical research models are either legally unusable (MPI family, GHUM) or heavier and less measurement-oriented (MHR); a better procedural model remains viable but spends its effort on exactly the regions where a sculpted mesh is free.

### Cited Findings
- MakeHuman's own solver for typed measurements is a per-measurement bisection over the slider range [-1, 1] with at most 10 halvings and a 0.01 cm tolerance, re-measuring a fixed vertex loop after each update **[read directly]** — [MakeHuman measurement plugin](https://github.com/makehumancommunity/makehuman/blob/master/makehuman/plugins/0_modeling_a_measurement.py)
- MakeHuman measure morphs are local: a girth target moves on the order of 400–1,300 body vertices, with maximum per-axis offsets of roughly 0.04–0.45 MakeHuman units (1 unit = 10 cm, per the ruler's ×10 cm conversion) at slider value 1 **[measured; unit conversion read directly]** — [anny 0.6.2 on PyPI](https://pypi.org/project/anny/); [MakeHuman measurement plugin](https://github.com/makehumancommunity/makehuman/blob/master/makehuman/plugins/0_modeling_a_measurement.py)

**Recommended measurement-enforcement pipeline for route B/C**
1. *Parameter vector.* w = [macro weights (gender, weight, muscle, proportions), 20 measure-morph weights, extra local targets (lowerarm scale/fat, head scale, foot scale, hip-scale for high hip), global height scale]. Keep each weight clamped to its authored range (typically [-1, 1]); allow mild extrapolation (e.g. ±1.5) only for local girth morphs.
2. *Measure function m(w).* Blend on CPU; for each girth, slice the body-part submesh with a plane at the measurement level (level defined by landmark vertices so it moves with the body), take the convex-hull perimeter for torso girths (bust, underbust, waist, high hip, hip) and thigh; raw slice perimeter is fine for near-convex limbs (calf, ankle, wrist, neck). Lengths are landmark-to-landmark distances or surface paths. For bust/hip take the max over a small band of levels, for waist the min, matching tailor practice.
3. *Solve.* Stage 1: least-squares fit of macro weights only to the big measurements (height, bust, waist, hip, inseam, weight-like girths) so the overall build is plausible. Stage 2: damped Gauss–Newton / Levenberg–Marquardt on the local weights using a finite-difference Jacobian J = ∂m/∂w (≈ 30–40 columns; each column is one blend + re-measure of only the affected rings, a few milliseconds for 13k vertices), with Tikhonov regularisation towards 0 so unassigned regions stay natural. Because measure morphs are local, J is nearly diagonal and 3–6 iterations should reach sub-millimetre residuals; MakeHuman's simpler per-slider bisection (10 steps, 0.01 cm) is a valid fallback but ignores cross-coupling (e.g. waist morph changing high hip).
4. *Exactness pass (local radial scaling).* For any girth still off after clamping (extreme sizes, or measures without a morph: elbow, forearm, high hip, head), apply a bone-local radial scale: for vertices in a soft band around the measurement plane, scale their offset from the limb/torso axis by s = target/current with a smooth falloff (e.g. cosine or smoothstep over ±5–8 cm along the axis) so neighbouring rings are not disturbed; iterate 2–3 times because hull perimeter is not exactly linear in s. For torso rings, scaling depth and width separately (keeping measured shoulder/hip width fixed) preserves front-view silhouette while matching girth.
5. *Order.* Lengths and height first (they translate large vertex sets and change ring positions), then torso girths, then limb girths, then the exactness pass; finally re-measure everything and display entered vs achieved values (as CLO does) rather than hiding residuals.
6. *Normals and rendering.* Recompute vertex normals after CPU blending; render with a single matte material; optionally draw the measured hull loops as tape lines.

**Risks to flag**
- Morph coupling and clamping: typed combinations far from human statistics (e.g. very small waist with very large hip) will exceed morph ranges; the radial pass will still hit the number but can produce creases. Provide a "plausibility" indicator instead of failing silently.
- Convex-hull vs raw perimeter choice must match how users measure; document it per measurement.
- Baking pipeline provenance: generate assets with a script that reads only CC0 files (base.obj, *.target) and keep that script in the repo together with the CC0 notice; do not vendor MakeHuman/MPFB2 Python code (AGPL/GPL) into the app.
- Anny's API has changed defaults several times in 2026 (rig, topology, pose parameterisation, compact blendshapes); pin the version if it is used for baking.
- Male/female handling: MakeHuman interpolates between gender anchors continuously; bust-specific measures (underbust, cup) need the gender weight or breast targets to be part of the solve.

### Gaps
- The exact-circumference procedure in steps 3–4 is an engineering design synthesised from MakeHuman's bisection, CLO's documented behaviour and standard plane-slice/hull measurement; no single published source prescribing this combined algorithm was retrieved, and convergence figures (iterations, milliseconds) are estimates that must be validated in the app.
- The achievable girth range of each MakeHuman measure morph (in cm, at weight ±1) was not computed; only the number of affected vertices and maximum offsets were measured. This should be measured before deciding how much extrapolation or radial scaling is needed.
- glTF-specific details (sparse accessors for morph targets, meshopt/Draco behaviour with morphs) were not verified against the glTF specification or three.js loader documentation in this pass; a custom binary + CPU blending avoids the dependency.
- MHR asset download size and whether its identity blendshapes are exposed in the FBX for every LOD in a browser-friendly way were not verified.
- No runtime benchmark of CPU morphing + slicing for a 13k-vertex mesh in the browser was run.
